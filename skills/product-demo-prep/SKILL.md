# Product Demo Prep

Prepare one accurate demonstration for the requested audience and environment.
Use synthetic data and the customer's authorized source material. Keep customer
names, recordings, credentials and results in private project artifacts.

## Inputs and prerequisites

Resolve the target product URL, environment, approved test identity, audience,
use cases, source material and permitted changes from the current request and
project documentation. Confirm access through the project's secure login path.
Missing configuration is a precise blocker; examples grant no live permissions.

Use the project's existing QA harness, browser tooling and release procedure.
No particular repository, service API, provider or internal account is assumed.
A demo request authorizes rehearsal and scoped preparation; product fixes,
shared-data edits, deployment, paid generation and sends require task authority.

## Prepare and rehearse

1. Choose three to five realistic audience questions and expected observable results.
2. Verify important facts against approved sources. Include a grounded question,
   a useful follow-up, a missing-information case and a boundary case.
3. Check the exact environment, tenant and effective role before running prompts.
4. Exercise the real UI or integration path. Record actual answers, source links,
   output artifacts and failures; a mocked response is not hosted proof.
5. Diagnose failures by layer: source coverage, retrieval, instructions, client,
   service contract or environment. Record an evidence-based hypothesis before fixes.
6. Make only authorized changes. Preserve before-state for configuration edits,
   rerun affected checks and verify one neighboring behavior remains correct.
7. Rehearse the exact public-facing wording after any change. Do not quietly
   substitute an easier prompt for a required customer question.
8. Inspect the final exports, not just a success message. Verify branding,
   references, readability, source facts, downloads and reload persistence.

Use the customer's named concepts when they help retrieve relevant sources,
but explain terminology for the audience. Use generic example prompts such as
"What does this organization offer?" and "Use the approved onboarding guide to
prepare a 30-minute introduction for a new team member."

## Evidence and handoff

Keep a private prompt scorecard: prompt, expected result, observed result,
source coverage, failure, repair, retest and proof tier. Keep logs and screenshots
free of tokens, personal inboxes and unrelated windows. Do not save raw sessions
or real customer records in a public skill archive.

Deliver the demo agenda, exact prompts, expected outputs, source references,
known limitations and verified environment/revision. Separate local, hosted,
authenticated and delivered proof. For recording, use `demo-video-production`.
For a broader QA request, use `full-suite-tests` when installed. Report missing
tooling or access directly rather than simulating a successful demo.
