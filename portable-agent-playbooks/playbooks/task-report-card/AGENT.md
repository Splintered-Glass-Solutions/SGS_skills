# Task Report Card Agent Playbook

This is a platform-neutral version of the `task-report-card` skill. It is designed
for use with Claude, Claude Code, Cursor, OpenAI agents, or another agent
platform that supports reusable instructions.

## Trigger

Create or update a concise HTML status report card for a long-running task spanning chats, including scope, evidence, blockers, Dev deployment, usage estimates, thread counts, and subagent counts.

## Portability Notes

- Replace `<agent-config>` with the local configuration folder for the
  target agent platform.
- Replace `<workspace>` with the user's active project/workspace root.
- Treat slash commands and `$skill-name` references as invocation hints.
  If the target platform does not support slash commands, paste this
  playbook into the agent's custom instructions or project memory.
- Keep all original safety gates. Do not send messages, deploy, mutate
  production data, change permissions, or perform irreversible actions
  without explicit approval from the user.
- If a referenced connector or tool is not available in the target platform,
  stop and report the missing capability instead of simulating external
  actions.

## Instructions

# Task Report Card

Create a self-contained, readable HTML report and keep it current through continuation handoffs. The user can open it locally without a service. Keep a companion JSON data file so a later chat can update the same report instead of reconstructing it. Render the [HTML template](assets/report-card.html) with `python3 <skill-dir>/scripts/render.py <report-data.json> <report.html>`. The renderer escapes data for embedding. No external deployment, sharing, or messages are implied.

## Status and proof gates

- Use the sequence `not_started` → `progress` → `local_working` candidate → verified local work → `done` (deployed to Dev) → `verified_dev` (fully verified in Dev). A candidate is explicitly labeled **local candidate; story not verified**, not an accepted working feature. In `local_working`, run `$run-user-story` and `$feature-finish-line` on the scoped feature before claiming it works locally. Execute these skills only within the user's actual authority, higher-priority rules and environment constraints; this report skill does not itself authorize database writes, migrations, deployments, external communication or other operations. When such a gate cannot be satisfied, preserve the evidence and, for work not yet deployed, mark it `blocked` or `progress` as appropriate.
- Record a passing story and finish-line evidence per item. A story that fails returns the item to `progress` for repair or `blocked` for a genuine blocker; an incomplete story is not a pass. Count “User Story Ran” only for a passed, evidence-linked story on a currently local item. Merely starting a story, exercising a synthetic slice, or having historical local checks does not count as a pass. For verified local work, include one or two real, feature-specific screenshots of the UI, terminal output, API result or data display, captured safely without secrets. Screenshots complement the story and executable checks; they do not replace them. If safe visual evidence cannot be captured, explain the gap and keep the item as a candidate or blocked rather than fabricating proof.
- `done` means the item has been deployed to Dev, regardless of whether local or Dev testing is complete or passed. Record deployment evidence and unresolved failures or blockers in its details. Use `verified_dev` only once the complete scoped feature is tested and working in Dev with passing, evidence-linked Dev proof. These statuses are mutually exclusive: total deployed includes both counts. A failed Dev test does not erase a proven deployment; keep the item deployed and describe the failure and next action. Respect any separate deployment gates and authorization applicable to the actual release. For legacy entries lacking structured evidence, preserve historical data and mark missing proof unknown; do not invent passes or silently rewrite history.
- Store optional `localProof` on each item as `{"story":{"status":"passed|failed|incomplete|not_run","evidence":"path or URL"},"finishLine":{"status":"passed|failed|incomplete|not_run","evidence":"path or URL"},"screenshots":[{"path":"path or URL","caption":"what the image shows"}]}`. Use one or two safe screenshots. Record `deploymentProof` with an evidence link or description identifying the deployed revision and environment. Store `devProof` as `{"status":"passed|failed|incomplete|not_run","evidence":"path or URL"}`. Evidence must identify the exact run, environment and revision in the linked artifact. Update fields and disposition together; do not leave an explicitly failed/incomplete story in `local_working`. The renderer's display is not a substitute for validating the evidence or a release authorization.

## Live elapsed timers

- Show three visible, updating wall-clock timers: since the last status update (`statusUpdatedAt`), since the most recent verified local feature (`lastLocalSuccessAt`), and elapsed since the task run began (`taskStartedAt`). Record timezone-qualified ISO 8601 timestamps only when supported by evidence. Advance the first when the status snapshot is actually updated, not merely because the page is opened; advance the second only when a feature meets the story, finish-line and screenshot gates. Retain the original task start across continuations. Optional `taskEndedAt` freezes the total once the task ends.
- Do not invent missing or uncertain event times or infer a successful feature from a status label. Show **Unknown** until supported timestamps are recorded; timestamps in the future or without a timezone are invalid. Timers are wall-clock elapsed time including pauses, not active labor or a live activity monitor. The page updates them locally while open; it does not retrieve new status or prove the agent is running. Preserve the previous snapshot and existing report data when adopting this schema.

## Keep the report live

- Treat the report as a maintained task artifact, not a one-time snapshot. Update the companion JSON and regenerate the same HTML at meaningful milestones: a decision or unblocker arrives, a blocker changes, implementation or review passes, a release or test changes the proof, an email is sent, or work pauses or resumes. Update the snapshot time and affected items; preserve the rest of the scope.
- Preserve `statusHistory` in the companion JSON. The renderer appends an observed, timestamped snapshot only when status counts change and at least 30 minutes have elapsed since the previous snapshot, or when history is empty. Continue updating the report at meaningful milestones, even if the chart does not change. Never fabricate prior points; preserve history during handoffs unless the user explicitly requests pruning. Each snapshot counts report entries, including disclosed overlaps, and includes all seven statuses; older snapshots lacking `verified_dev` remain untracked rather than inferred as zero.
- When the user selects an item's A/B/C path, record the choice promptly (`selected: true`) and move undeployed work to `progress` while executing or verifying it; keep a proven deployed item in its deployment status; a selection is not completion. If the selected action is attempted or reviewed and a specific existing or new obstacle prevents further progress, for undeployed work return the item to `blocked` and set `blockerState: "after_answer"`; for deployed work retain the deployment status and and record the attempt, current obstacle, evidence and next action. If a new decision is needed despite an earlier selection, set `blockerState: "needs_decision"` and explain the new question; never discard the prior choice. Clear stale blockerState when no longer blocked. Do not ask the user to repeat an already authorized decision. Use green only after Dev deployment is proved; show verified Dev work in its own status.
- Make each path a keyboard-accessible click-to-copy control that copies the item ID, letter and path label in a format the user can paste into chat. Show clear success or failure feedback and offer a selectable fallback if clipboard access is denied. Copying alone does not send a message or change the saved decision; apply a choice when the user communicates it.
- Add a checkbox beside each path and a bottom-corner sticky bulk-copy control that appears only when paths are checked and copies all checked item IDs, letters and labels as separate lines. Preserve selections while filtering and offer clear-selection and selectable clipboard-failure fallback. Checkbox selections are temporary and do not change recorded decisions; do not preselect them from prior decisions.
- Keep options honest and concise: show the current blocker and practical paths, flag unverified alternatives and avoid fabricating a third path. Mark the chosen path separately from a recommendation; do not imply that selecting it completed any work. Interpret authority according to the action the user actually chose and its stated scope.
- Refresh usage and chat/agent counts when reliable current measurements are available. Otherwise retain the prior values, mark their measurement time and limitations, and use defensible estimates or minimums rather than inventing numbers. Do not sum incompatible accounting methods or overlapping agent time.
- In every continuation handoff, carry the report and data paths, last snapshot, decisions and authority, current blocker, known accounting limits and next milestone update. Reuse the existing report in the new chat; don't create a disconnected replacement. A static HTML file updates when regenerated and may require the reader to refresh the open tab; do not imply automatic real-time syncing.

## Resource history

At meaningful milestones, record actual observations in `resourceHistory`; do not invent historical points. Use `scripts/capture_resources.py <report-data.json> --thread-id <current-chat-id> --session-file <current-chat-jsonl>` when the local session file is available, then render. It records approximate available RAM (free plus file-backed pages), physical RAM, reported pressure and the latest measured per-response context input/window; omit unavailable measurements. Context fullness is input divided by window for each chat, not cumulative usage or cost. Preserve earlier samples and show timestamps, chat identity and a tabular fallback. Sampling occurs at milestones, not continuously; do not claim a live monitor. Do not connect context lines across different chats. The report's narrow status-history bars remain accessible through labels and the counts table.

## Five-second scan

- Above the fold, show the task name, snapshot time, the most important current blocker or next action, and seven clear status counts. Show each status count's percentage of all report entries as small subtext in the same status color, accounting for overlapping entries as disclosed. On the blocked tile show counts needing a new answer and blocked again after an answer, plus the total number of entries with recorded answers. Count entries, not unique issues; retain explicit overlap disclosure. Make each count a keyboard-accessible toggle: activate to filter by that status, activate again to show all; keep the status selector synchronized and indicate the active filter without relying on color. Keep chat, subagent, token and elapsed totals in the numbers disclosure. Add a short, plain-language explanation of the task goal near the title.
- Show a compact 100% stacked status-history bar chart near the counts: green deployed, blue verified in Dev, teal local candidate or verified local work, blue in progress, red blocked, gray not started, and purple intentionally deferred. Each bar represents a recorded status-count snapshot and normalizes by that snapshot’s entry total; preserve a readable legend, accessible count table, timestamp, and overlap disclosure. A single starting bar is honest when no history exists.
- Default to short item names, status indicators and plain-language summaries. Put evidence, detailed blockers, per-item usage, methodology and source notes behind expandable item or section details; tuck lengthy evidence histories into a further disclosure while keeping all source data available and searchable. Avoid paragraphs, repeated legends, or long descriptions above the work list.
- When the headline represents a specific blocker, make it expandable in place with that item’s copyable possible paths and synchronized bulk-selection checkboxes. Link it explicitly by item ID; do not attach an unrelated blocker’s options to a custom headline.
- Under each item title, provide a short plain-language summary; in its expandable details provide a brief A/B/C set of possible paths, using the decision-focused style of [interview-spec](../interview-spec/AGENT.md). Keep item details collapsed by default so the report stays compact; reveal blocked paths when an item is opened. State the actual obstacle, what it affects, the next action and a practical tradeoff for each viable path. Mark a recommendation only when supported by the evidence.
- Make explanations specific to the item and understandable to a nontechnical reader. For work already underway, say what remains to prove or do; do not present it as broken. Treat options as informational, not clickable approvals. Preserve settled decisions and existing authority: do not ask the user to redecide them, invent dependencies, suggest an unauthorized action as already approved, or claim a workaround is verified when it is only a proposal. If fewer than three honest paths are known, show those available and explicitly identify the remaining path as needing investigation instead of fabricating choices. Only request input where a real unresolved decision requires it.
- Set `headline` with a short `title` and `note` grounded in the current task. If no blocker exists, describe the current focus without labeling it blocked. Make text labels convey meaning independently of color and clearly distinguish historical/reconciliation counts from active work.
- Use compact accessible icon controls for the status dropdown and expand/collapse actions, with labels for assistive technology. Keep count labels, long titles, status badges and choices readable without clipped or cramped wrapping. On narrow screens let status badges move below item text and let controls wrap; maintain clear focus and comfortable spacing.
- Make the snapshot time human-readable with a timezone and retain the original timestamp for inspection. Give readers a visible shortcut from the header to the searchable work list. Use subtle status accents and compact, separately readable blocked-decision counts; preserve text labels and keyboard focus rather than relying on color.
- Validate the first screen at desktop and mobile sizes: the task, current focus, status counts and usage totals should be understandable quickly, without clipping or horizontal page scrolling. Iterate only on visible issues.

## Evidence and scope

- Recover the exact task, scope, ledger, prior report and continuation chain. Include every explicitly selected item and the relevant QA/QC backlog, including subitems where available. Read the real source list; do not count blank template rows as work. Retain original IDs, titles, source links, dates and reported statuses.
- Reconcile relevant repositories, release SHAs, deployed environment and current evidence when inexpensive and consequential. Separate local, merged, deployed Dev, production, provider and customer acceptance. Historical reports and sheet statuses are evidence, not automatic current truth. Surface conflicting or missing evidence instead of hiding it.
- Enumerate additional reports in conversation threads and linked trackers where accessible. Deduplicate only when identity is established; otherwise display separate records and state overlap. Include unknown or inaccessible sources as a clear coverage limitation.
- Show seven statuses with both text and color: green for deployed to Dev awaiting full verification, a distinct blue for verified in Dev; teal for a local candidate or verified local work, explicitly distinguishing the two using the proof gates above; red for an evidenced blocker; blue for in-progress work or explicit reconciliation, with a rough completion percentage when defensible; grey for work not started; purple for work explicitly deferred or sidelined, with the decision and reason retained. A successful build or partial test alone does not establish that a whole item works locally. Explain the local evidence, its limits, and remaining Dev work. An undeployed selected item remains in progress while its chosen work or verification can proceed; return it to blocked only when a specific obstacle prevents the next step. Keep deployed items in the appropriate deployment status and describe any outstanding obstacle. Never label old work “not started” without qualifying the new scope. For unknown status or percentage, say unknown; do not invent data to fill a cell.
- Show a short next step or blocker per item where known, plus per-item token and time usage. Prefer measured values or bounded estimates with a stated basis; use `Unknown` when allocations cannot be supported. Do not allocate the entire parent total to every child or sum overlapping phases.
- Put status counts at the top; keep delivery chat counts, distinct descendant subagent runs, aggregate tokens and elapsed time in the numbers disclosure when available. Label the population and timestamp. Distinguish elapsed from human labor and concurrent agent time; avoid double-counting handoffs. State whether token counters include cached/repeated context and whether descendants are included. Never present token counters as cost.
- Use the task's durable handoff and available thread tools to identify predecessor and successor chats. Do not create or modify chats just to produce a report. If only partial thread history or subagent records are accessible, label counts as minimums or unknown.
- Status counts must say whether they count parent and child entries, duplicates, or unique items. Don't imply a single overall completion percentage from uneven scope. Status controls and text must remain usable without color vision.

## Template data

`resourceHistory` (timestamped RAM and per-chat context observations; omit unknown measurements), `statusHistory` (observed snapshots at least 30 minutes apart with `at`, `updateLabel` and all seven `counts` (older snapshots may omit `verified_dev`)), `title`, `updated`, `subtitle`, `goalSummary`, `headline` (optional `{title, note, status, itemId}`), `threads`, `agents`, `tokens`, `elapsed`, `tokenBasis`, `elapsedBasis`, `checkpoint`, `sources`, and `sections`. Each section has `title`, `description`, and `items`. Each item has `id`, `title`, `status` (`done`, `verified_dev`, `local_working`, `blocked`, `progress`, `not_started`, `deferred`), `progress` (number or null), `detail`, `time`, `tokens`, `plainSummary` (short plain-language explanation), and `options` (up to three objects with `label` and `description`, plus optional `recommended: true` or `selected: true`). Present choices in A/B/C order and explain uncertainty or deferral where applicable. For older blocked items without these fields, show a clear missing-analysis message rather than inventing a summary or options; keep other older rows compact and update their data when asked. Optional `blockerState` (`needs_decision` or `after_answer`) distinguishes the current blocker from a prior selected option; use only for blocked items. Without it, an item with a recorded option defaults to after-answer and an item without one defaults to needs-decision. Optional `sheetStatus`, `sheetRow`, `priority`, `environment`, `source`, `note`, and `usageNote` preserve provenance and measurement basis. Use null for unknowns.

## Verification and handoff

Check that the HTML opens, its embedded data parses, each source item is present, explanations and options are present and accurate, the status counts match the rendered items, links use verified destinations, search/status filters include the new text, and readable desktop/mobile views show no broken layout. Check that blocked details are discoverable and that older data without the new fields renders without errors. Record any inaccessible scope or unverified status. During `$continue-in-new-thread`, include the report path, data path, last snapshot time, source pointers and next update action in the handoff; do not reset counters across successor chats. Return the report link and any material coverage or accounting limits.
